# WildBlocks code audit and optimization record

Audit date: 2026-10-06. Scope: the TypeScript/React game, procedural content, persistence, workers, all four game contexts, UI/input, build configuration and existing tests. This is a conservative code and regression audit; it does not certify every browser, network or physical device.

## Outcome

The game already has useful foundations: strict TypeScript, deterministic generation, typed events, separate UI stores, worker generation/meshing, instanced furniture and particles, spatial indexing, incremental terrain saves, and meaningful automated tests. The main problems were accidental eager engine imports, unbounded or repeated work in hot paths, incomplete resource cleanup, and asynchronous save/worker edge cases.

Changes preserve content IDs, generation seeds, save schema/version, recipes, equipment stats, movement equations, collision rules, combat values and network protocols. Lower graphics settings intentionally show less terrain/detail. No gameplay feature was intentionally removed. Existing behavior is checked by the original suite plus focused regression cases; physical-device and full multiplayer playtesting remain necessary.

## Findings and implemented changes

| Area | Evidence / previous behavior | Change and safeguard |
| --- | --- | --- |
| Menu loading | UI imports of `Game`, `AssetManager` and `BuildIcons` pulled Three and engine dependencies into the initial page despite `GameView` being lazy. | UI reads a lightweight registry and icon URL cache. Registry types use type-only imports. `Game.current` remains a compatible alias backed by one registry. Production output verifies Three loads with the game rather than the menu. |
| Worker failures | Callbacks captured numeric worker indexes, which shifted after removal. Retrying failed mesh jobs reused buffers already transferred/detached. Partial constructor failure left workers running. | Callbacks identify the actual Worker; failed jobs reject so streaming can reconstruct inputs. Failed/partially started workers terminate. Cancellation, disposal, posting errors and shifted-index recovery have regressions. |
| Terrain streaming | Older mesh results could replace newer edits or a new record at the same coordinates. Mesh preparation could fill all available slots in one frame. Upload loop used an OR condition that defeated its intended limits. | Results carry record identity and version. Stale results are discarded and remeshed. Preparation/upload each attempt at most two chunks with a four-millisecond budget between chunks. One expensive chunk can still exceed the budget; individual work is not preempted. |
| Repeated column queries | `standableY` scanned a vertical column with repeated world/chunk lookups on every call. Used by spawning, movement/navigation and terrain-dependent systems. | Versioned per-chunk column cache uses typed arrays and direct block reads. Chunk edits/replacement invalidate it. Tests compare against the original scanner across generated worlds, negatives, water, slabs, edits and reloads. |
| Saves during edits | Dirty chunk keys were cleared after asynchronous storage, potentially forgetting edits made while saving. State/terrain/metadata/maps used separate transactions. | Capture dirty terrain before yielding; new edits remain dirty; failures restore pending keys. All save records and the previous-state backup commit in one IndexedDB transaction. Clone-error rollback and concurrent-edit persistence are tested. |
| Save & Quit / sharing | Concurrent `saveNow` calls returned immediately, allowing quit/sharing before an active save finished. Errors were swallowed, so callers could leave despite failure. Map tiles were removed from the queue even on failure. | Save requests share a tracked promise. Explicit requests wait and take a fresh snapshot; failure returns `false`. Quit/shared-project exit/sharing retain the session on failure. Map tiles return to the queue. Build dirty status only clears if no new block/object edits exist. |
| Low-end graphics | Build Home forced render distance to at least six even when a lower setting was chosen. Auto stopped before reaching lighter available settings. Frame samples were accumulated in an array. | All modes respect selected distance. A shared helper calculates pixel ratio; Auto can reach distance three and scale 0.5, then disable shadows/clouds and reduce high particles. Samples use a running sum/count and reset outside active sampling. Pure regressions verify limits and reduction order. |
| Large creative projects | Object lighting copied the entire furniture map every 50 ms while sampling only 24 entries. Animation copied a Set each frame. Empty spatial-index cells accumulated. | Persistent iteration visits lighting samples without full-project copies. Iterate the animation Set directly; remove empty index cells. Existing placement, collision, door, farm and undo tests remain applicable. |
| Repeated calculations / allocations | Duplicate spring integrators, duplicated frame-tail logic, new motion vectors per body/gun frame, new arrow geometry per shot and projection-matrix updates every frame. | Share the original spring equations and frame finishing routine. Reuse/scalarize temporary motion data and share immutable arrow geometry. Recalculate view-model projection only on aspect changes. Mode-specific rain/light behavior is retained. |
| Crafting UI | Sorting called recipe availability repeatedly; availability can simulate inventory removal/output placement. | Memoize filtering and evaluate availability once per recipe per inventory/station/level change; reuse results for sorting and rows. Recipe rules stay in `CraftingSystem`. |
| Rendering ownership | Held preview planes, build helpers, overlays and muzzle-flash assets were not released on teardown. Global combat-text cache could dispose textures used by active sprites. | Dispose session-owned resources. Combat text uses a per-session cache with active-user tracking and idle-only eviction. Shared terrain, model and object materials remain shared; tests check active texture and held-preview ownership. |
| Help content | Important touch, save, difficulty, voice, build and Deathmatch rules were scattered or missing. Some old documentation overstated safety, rebinding and offline support. | Searchable seven-topic How to Play, current-binding controls, and a generated player manual share `playerGuide.ts`. README descriptions are corrected; developer and device-QA guidance are documented. |

## Reuse decisions

Reusable implementations now include `core/Spring.ts`, `core/graphics.ts`, `core/iconUrls.ts`, `game/registry.ts`, the frame-finishing method, and shared guide/control data. Existing `InventoryLogic`, crafting rules, coordinate conversions, generation, block registries, build commands/history and material caches are already the right places for shared behavior.

Some similar-looking code should stay separate:

- Worker entry and main-thread fallback call the same generation/meshing functions but have different execution and transport lifecycles.
- Survival interaction, creative construction and Deathmatch combat have different rules; combining them into one large generic controller would hide those rules.
- PvP trusts local gameplay while Deathmatch uses a host referee. Shared transport is appropriate; replacing both authority models is a separate gameplay/network project.
- Model/object caches and icon textures are shared. Terrain materials/atlases belong to AssetManager and are shared within their renderer. A single mesh/helper must not dispose a resource owned by one of these shared owners; instances, private helper geometry and private textures can be cleaned up directly.
- Large content tables are declarative content, not redundant logic. Block ordering and stable keys are persistence contracts.

The audit did not blindly delete exported helpers, old-save paths or content based on text-search absence. They can be compatibility, worker, debug or dynamic entry points. Large files are candidates for future extraction only with focused behavior coverage.

## Measured validation

Baseline: 258 tests in 18 files, strict typecheck and production build passed. Content validation reported 112 blocks, 172 survival items, 133 recipes, 61 architecture materials, 279 catalog items and 154 furniture models; all 172 survival items are obtainable.

The final production build reduced eager JavaScript from about **1,853.58 kB to 708.10 kB** (index plus HTML module-preload dependencies; about **62%**). Gzip fell from about **550.61 kB to 221.52 kB** for that same initial dependency set, including the expanded guide. Three and game code still ship when a player starts a world; this is deferred loading, not removal of engine functionality.

Final verification: **305 tests pass in 26 files** (47 more tests than baseline), strict TypeScript and the Vite production build pass, content validation passes, and the player manual regenerates successfully. Regressions cover worker recovery, terrain upload/versioning, column-cache equivalence, atomic/concurrent saves in IndexedDB and the temporary-memory fallback, save coordination, graphics floors and resource ownership. The streaming count-cap test uses a fixed clock; a separate elapsed-time test verifies stopping after one expensive preparation/upload, avoiding assumptions about the test machine’s speed.

Browser checks use a fresh isolated Chrome profile, avoiding existing user worlds. Desktop and emulated phone-landscape guide layouts have no horizontal overflow; topic switching and cross-topic search work. A Survival world loads with workers, then a placed block, three inventory torches and player position survive Save & Quit and reopening. A simulated failed save keeps the pause screen and re-enables the quit button; retry succeeds. A subsequent Build Home session loads at Low graphics with distance four, accepts a live change to distance three, renders its catalog, and saves three test objects added through the engine (door, chair and light). This is a limited local smoke check; emulation is not a substitute for physical-phone performance, complete touch gameplay or real online/voice testing.

## Shared-world joining and Deathmatch loading follow-up

A direct **Join Friend’s World** entry in the main menu and Worlds screen opens the existing code-join form. The host's source settings still select shared Survival or Build Home automatically; invite links and the original PvP create/join flow remain. The room bar labels its six-character code, and How to Play/manual explain where the host opens a map and how the guest joins without a link. The main menu can scroll when short screens or larger UI scaling make its buttons taller than the available space.

Deathmatch previously generated all survival icons before city loading, required 29–49 nearby meshes, and kicked unfinished clients after 30 seconds including the first lazy engine download. It now skips unused icons, requires 13 generated/meshed spawn-neighbourhood chunks at normal distances, and gives clients up to 90 seconds. Outer terrain still streams at the selected distance. The ten-second preparation and match rules are unchanged. Readiness now requires actual terrain completion rather than accepting a 25-second timer expiry.

Added regressions cover slower clients joining preparation after 45 seconds, bounded removal of clients that never load, spawn-first startup at multiple render distances, readiness past the old cutoff, cancellation, and code-only shared-map handoff for Survival and Build Home. Rendered-form checks verify direct code entry, the original host form and invite-code prefilling. Browser plugin setup is unavailable in this session; these follow-up checks do not establish physical-phone or live online behavior. The user's exact Deathmatch error/device was not supplied, so this addresses the confirmed loading-timeout path rather than proving every possible mobile connection issue resolved.

Shared Build Home now reuses the existing PvP player radar for hosts and guests, reading the same received positions without additional network messages. The shared-project header and tool palette reserve space for the radar; phones/tablets use a smaller disc and retain a scrollable tool drawer. The radar is not mounted in solo projects, Photo mode or with the HUD hidden. Production build/typecheck and 15 existing location/code-join tests pass. Rendered-component checks cover host, guest, solo, Photo and hidden-HUD visibility. Visual placement and live tracking on physical devices remain part of the acceptance matrix.

The tablet Recipe Book clipping issue is fixed by separating scrollable recipe information from the non-shrinking Craft/batch/All footer, allowing an overflowing crafting column to scroll and limiting the compact recipe list height. Crafting rules, ingredients and quantities are unchanged. An isolated browser preview of the real InventoryScreen verified enabled Arrow ×6 controls and click requests for one, five and all eight available crafts at 1280×730, at 1.4 UI scale, at 844×390 and at 568×320 with 1.2 UI scale. The preview used a temporary inventory and recorded engine calls; it did not modify a saved world. The production build/typecheck and 14 crafting/inventory tests pass. These are emulated layout checks, not physical iPad browser validation.

## Remaining performance risks and next work

| Priority | Risk / limit | Next evidence to collect before changing behavior |
| --- | --- | --- |
| High | A single mesh job, padded-volume copy, fallback generation or upload can exceed a frame budget. Main-thread fallback uses an eight-millisecond loop budget between complete jobs, not preemptible jobs. | Profile long tasks during fast travel on a real slower device. If needed, introduce resumable work or smaller meshing tasks with seam/version tests. |
| High | Very large construction commands, selections and up-to-400k-block blueprints are synchronous and can hitch. | Measure worst-case paste/undo/delete; move validated preparation off-thread or split application while retaining one atomic undo command. |
| High | Mobile GPU fill rate and thermal throttling vary greatly; high-DPI defaults favor sharpness. | Test Low/Auto on actual Android and iOS hardware for at least 15 minutes; record frame-time distributions rather than one FPS sample. |
| Medium | Worker count uses CPU concurrency, not memory capacity. Each in-flight mesh has a padded block/meta volume and output buffers. | Measure worker memory/throughput on low-RAM devices before reducing concurrency or adding device heuristics. |
| Medium | `Game`, `BuildMode`, `PvpSession` and `DeathmatchSession` coordinate many responsibilities. | Extract cohesive lifecycles/controllers incrementally with mode/input/save regressions. A wholesale split would add avoidable risk to this patch. |
| Medium | Menus still eagerly include multiplayer/voice code and procedural content needed by UI. | Profile menu interactions and consider lazy route chunks for PvP/Deathmatch without delaying invite handling or disconnect behavior. |
| Medium | Peer-hosted lifecycle, tab suspension, reconnect, voice permissions and browser audio vary by platform/network. | Run the multiplayer matrix below; network protocols were deliberately preserved. |
| Medium | Shutdown saves and a one-state backup cannot protect against every abrupt close, browser eviction or manual deletion. | Consider explicit export/import and full world-version backups as separate features with schema/migration tests. |

## Device and feature acceptance matrix

Run on desktop Chrome/Firefox/Safari, an integrated-GPU laptop, a slower Android phone, a recent Android phone, iPhone and iPad in landscape. Use normal site storage, then a separate temporary/private profile to exercise the storage warning.

1. Create Survival with a fixed seed; gather, fell a tree, craft, equip gear, place/remove blocks across a chunk boundary and use chest storage. Save, quit, reopen and verify position, inventory, terrain, chest and progress.
2. Till/plant/water/harvest; unload/reload the crop area. Sleep/set Home, ride/dismount/pick up a boat. Check difficulty-dependent death loss and recovery.
3. Travel through meadow, forest, water and caves for 10–15 minutes. Watch F3 frame time/FPS, pending workers, chunks, draw calls, triangles and available memory information. Compare identical seed/route/profile across builds after warm-up. Track p50/p95/p99 frame time and >50 ms frames externally where possible.
4. Create Build Home; place all major tool types, furniture, lights, doors/windows and growing crops. Exercise select/move/rotate, copy/paste, blueprints, undo/redo, fly, free camera, walkthrough, photos and location controls. Save/reopen. Test distance three, four and six.
5. Repeat world/project entry and exit five times. Resource counts should stabilize after shared caches warm up; they need not return to zero.
6. Check touch movement/look/hold/tap/slot split on phones/tablets, gyro permission and tuning on supported hardware, rotation prompts, UI scaling and scrolling. Emulated touch cannot verify motion sensors or browser permission UX.
7. Test two tabs with Same device, then two physical devices online for PvP, shared Build Home and Deathmatch. Verify lobby, host start, damage, respawn, pickup, reload, healing, score/results and host departure. Test Talk/Listen, audience and mute with permission granted and denied.
8. Force a save error in a throwaway profile (blocked/full storage), then retry. Quit/sharing must retain the session on failure, and edits made during an earlier save must survive the successful retry.

Do not claim a guaranteed frame rate or universal device support until this matrix has been run on the intended release hardware. This patch addresses identified costs and correctness issues without reducing simulation rules.

## Follow-up: loot, night enemies, untimed rooms and furniture rest

Wildlife melee previously applied only a one-point nudge, and its defeat path returned before loot generation. Untamed wildlife now receives normal weapon damage and drops species meat; other creature types have a guaranteed material drop. Feeding, gifts, Harmony penalties, protected tamed Fenns and hostile-only progression remain. Ten species have raw/cooked meat pairs, with Cooking Fire recipes. Skeleton bones supply an additional arrow recipe. New recipes are appended, preserving existing recipe IDs.

Zombies and Skeletons add distinct lightweight procedural models and sounds to the existing night ecosystem. Both chase and strike at close range, retreat at dawn, and honor Peaceful/creative settings. Hunting waves and normal groups now respect the same nearby hostile caps, including the gentler first night.

Shared world and Battle rooms have no countdown, including legacy saved/received settings; Deathmatch remains timed. Battle takedown limits remain available. World-time broadcasts continue. Bed proximity buttons open existing home/rest choices; Build Home object beds can advance even locked daylight. Shared-world guest rest is checked by the host before applying morning and recovery.

Chair, stool and sofa proximity buttons seat the player. Clear headroom and exits are checked; movement, jump, Interact and Stand up leave the seat. Damage, teleports and changed furniture are handled. Save snapshots use an exit position. Friends see the seated pose through the existing position messages. Proximity scans run at four Hz and use the object spatial index; UI stores only publish changed furniture.

Verification: 357 automated tests across 29 files, production build/typecheck, and data validation (193 obtainable items, 144 recipes, 279 catalog entries, 154 object models). The generated player guide contains seven topics and 51 entries. An isolated Chrome preview verified Sleep/Sit/Stand up clicks, minimum 44-pixel touch targets, viewport bounds and hiding for overlays/HUD/Photo/Build camera at desktop, tablet, landscape phone, small landscape phone and narrow portrait sizes, including larger text. The new creature models were visually inspected. These are local tests and browser emulation; live cross-device networking and physical low-end hardware remain outside the verified evidence.

## Follow-up: immediate respawn outside Deathmatch

Survival automatically respawns at Home, falling back to starting camp. The existing difficulty-specific drop handling, death event, satchel marker, 75% Vitality, minimum 60 Energy and three-second protection remain; a toast replaces the interrupting death screen. Shared Battle and Build together respawn immediately with their existing kit rules after publishing death, loot and score events. A host's Battle-ending death remains on results. Deathmatch retains its authoritative five-second respawn delay, and creative Build Home retains immunity to damage.

Both automatic respawn paths mark unloaded ground immediately so movement and spawn protection wait for terrain. Lethal void damage no longer runs a second rescue after a home spawn. Incoming PvP hits now establish attacker credit before synchronous damage, keeping a final hit attributed correctly and preventing its credit from being rewritten after respawn. Blocked and protected hits retain prior credit. The unused PvP five-second constant and countdown update were removed after checking all callers; existing HUD state remains compatible at zero.

Verification: **377 tests pass across 30 files**, strict TypeScript and the production build pass, and the seven-topic player manual regenerates. Twenty new regressions cover all survival difficulties with/without Home, drop coordinates and amounts, unchanged equipped gear, safe/blocked/unloaded spawns, lethal and nonlethal void falls, creative and Deathmatch separation, host/guest Battle and co-op deaths, kit refills, ordered death/alive messages, lethal-hit credit, blocked/protected hits and round-ending results. Physical-device performance and live cross-device networking were not retested for this change.

## Follow-up: Pause-panel rescue while alive

The requested living-player escape now appears directly below Resume / Keep building in Survival, PvP/shared-world and Build Home Pause panels. One shared button calls `Game.quickRespawn`; it returns a failure reason rather than closing Pause when rescue cannot proceed. Survival returns to Home/camp without item loss, health/energy refill, death events or progression changes. Build Home uses existing collision-checked navigation and both-camera updates at the lot entrance. Shared survival/Battle uses existing near-player rescue, combat checks and its eight-second cooldown. Boats dismount before rescue, unloaded ground freezes movement, and existing longer protection is preserved. Deathmatch does not expose or accept Quick Respawn.

Pause button containers previously had a minimum width larger than the narrow panel's inner width. They now shrink correctly; the rescue target stays at least 44 pixels high and explanations wrap. No recurring UI polling was added.

Verification: **392 tests pass across 31 files** and the production build/typecheck passes. Fifteen new regressions cover rescue health/items/progress, Home/camp fallback, boat exit, loading/protection, rejected states, friend-room rules, Build terrain/furniture/failure handling and Pause visibility by mode. An isolated Chrome preview verified actual button clicks, preserved health/energy/inventory, Home/camp/Build/friend destinations, failure feedback, Deathmatch absence and viewport bounds at 1280×730, 1024×600, 844×390, 568×320 and 320×568, including UI scale 1.2/1.4. Screenshots were visually checked; the temporary preview fixture was removed. How to Play and the generated guide now have seven topics and 52 entries. These checks use local fixtures and emulated viewports; physical devices and live cross-device networking were not exercised.
